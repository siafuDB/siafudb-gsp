# GSP wire format v0

Status: **draft, unaudited, implemented in `crates/gsp-wire`**. Every rule
below is enforced by that crate and exercised by its tests; the test vectors at
the end are generated by `crates/gsp-wire/tests/vectors.rs`, which fails if
this file goes stale. Nothing here has had external cryptographic review.

This document is meant to be sufficient to write a second implementation
(TypeScript is the expected one). Where it says MUST, the Rust implementation
rejects the alternative.

Out of scope for v0: transport, session key exchange (hybrid X25519 +
ML-KEM-768 is planned; only its registry ids exist), the schema of an op's
`payload`, how a fragment key is distributed, and how a peer decides to trust
an author's genesis entry.

## 1. Encoding

Everything is CBOR (RFC 8949) in the **core deterministic encoding** of section
4.2.1, restricted to a subset.

Allowed data items:

| Item                    | Notes                                      |
| ----------------------- | ------------------------------------------ |
| unsigned int            | major type 0, `0 ..= 2^64-1`               |
| negative int            | major type 1, `-2^64 ..= -1`               |
| byte string             | definite length                            |
| text string             | definite length, valid UTF-8               |
| array                   | definite length                            |
| map                     | definite length, **text-string keys only** |
| `false`, `true`, `null` | `f4`, `f5`, `f6`                           |
| float                   | `f9` / `fa` / `fb`                         |

Not allowed anywhere: tags, indefinite lengths, `undefined`, other simple
values, non-text map keys, bignums. Maximum nesting depth is 32.

Deterministic rules (encoder MUST produce, decoder MUST require):

1. Integers and all length prefixes use the shortest form.
2. Map keys are sorted by the bytewise lexicographic order of their encoded
   form. For text keys this means: shorter UTF-8 byte length first, then
   bytewise. No duplicate keys.
3. A float is encoded in the shortest of binary16, binary32, binary64 that
   represents the value exactly. Every NaN is `f9 7e 00`. `-0.0` is `f9 80 00`.
   Floats are never converted to integers or the reverse: `1.0` is `f9 3c 00`,
   `1` is `01`, and they are different values.
4. Exactly one data item; no trailing bytes.

**Decoder strictness.** A conforming decoder parses the item, re-encodes it
with the rules above, and rejects the input unless the re-encoding is
byte-identical. This is how the Rust implementation does it; it makes
"canonical" a property that is checked rather than assumed.

**Decoder cost.** Frames are decoded before anything is authenticated, so a
decoder MUST NOT let the input decide how much it allocates:

- a claimed array or map length larger than the number of input bytes left is
  an error, checked before anything is reserved for it;
- map keys are checked **while decoding**: each key's encoding MUST be
  strictly greater, bytewise, than the previous one, and the decoder fails at
  the first key that is not (equal: duplicate key; smaller: not canonical). A
  megabyte of repeated keys fails at its second key;
- a decoder bounds the total number of data items (arrays, maps, map values
  and scalars each count as one) by what the structure being read can hold. An
  in-memory item is many times larger than a one-byte item on the wire. The
  Rust implementation allows 65 536 items per frame (section 10), 128 for a
  `Signed` envelope, 8 for a `SealedOp` header and 4 for a `Plain`.

**TypeScript notes.** Integers above `2^53` occur (`u64` clocks and sequence
numbers fit, but the type allows the full range): decode integers as `bigint`
or reject values you cannot represent, never round. JavaScript has one number
type, so an implementation MUST keep "integer 1" and "float 1.0" distinct in
its value model.

In the grammar below, `uint` is an unsigned integer, `bstr` a byte string,
`tstr` a text string, `[a, b]` an array, `x / y` a choice, `* x` zero or more.
All structures are **arrays with positional fields**; maps appear only inside
`payload`.

## 2. Registries

Numeric, append-only, `0` invalid. Ids are carried as `uint` and MUST survive
a round trip even when unknown.

| Registry | Id  | Name               | In this implementation                  |
| -------- | --- | ------------------ | --------------------------------------- |
| SigAlg   | 1   | Ed25519            | yes (strict verification, see 5.3)      |
| SigAlg   | 2   | ML-DSA-65          | yes (FIPS 204), unless built without it |
| HashAlg  | 1   | BLAKE3-256         | yes, default                            |
| HashAlg  | 2   | SHA3-256           | yes                                     |
| HashAlg  | 3   | SHA-256            | registered only: treated as unknown     |
| KemAlg   | 1   | X25519             | registered only                         |
| KemAlg   | 2   | ML-KEM-768         | registered only                         |
| AeadAlg  | 1   | XChaCha20-Poly1305 | yes                                     |
| AeadAlg  | 2   | AES-256-GCM        | registered only                         |

**An implementation may omit an algorithm.** The table says what the Rust
crate implements with its default features; built without its `ml-dsa`
feature it does not implement ML-DSA-65, and a TypeScript port may start with
Ed25519 alone. A registered algorithm that an implementation does not have is
handled exactly like an id it has never heard of:

- parsing is unaffected: keys, signatures and policies carrying the id are
  read, kept and re-encoded unchanged, and content ids do not depend on it;
- a signature of that algorithm cannot be checked, so the op is `Unverifiable`
  (`UnknownSigAlg`), never `Valid`, and never `Invalid` on that ground
  (section 6). A bad signature of an algorithm the implementation does have
  still makes the op `Invalid`;
- a key-log entry that needs the algorithm (a genesis or `SetPolicy` whose
  policy lists it, or an entry signed with it) is not applied (section 5,
  rule 5): the log stays where it was, and for a genesis there is no log;
- the object is kept and evaluated again by software that has the algorithm.
  It is not dropped as invalid and not counted against its author.

So an Ed25519-only implementation can take full part in a fragment whose
authors all have the policy `[1]`, and cannot verify, and so does not apply,
the ops of a hybrid author.

`format` is the structure version. This document defines `format = 0`. A
structure with another `format` is `Unverifiable` (section 6), not invalid.

## 3. Common structures

```text
Multihash = [alg: uint, digest: bstr]          ; alg is a HashAlg id
PublicKey = [alg: uint, key: bstr]             ; alg is a SigAlg id
Signature = [alg: uint, key_id: Multihash, sig: bstr]
Signed    = [body: bstr, sigs: [* Signature]]
```

- `Multihash.digest` is 32 bytes for HashAlg 1, 2, 3. For an unknown `alg` a
  decoder accepts 1 to 64 bytes.
- `PublicKey.key`: Ed25519 is the 32-byte RFC 8032 public key; ML-DSA-65 is
  the 1952-byte FIPS 204 encoded public key.
- `Signature.sig`: Ed25519 is 64 bytes; ML-DSA-65 is 3309 bytes.
- **Key id.** `key_id(K, h) = Multihash(h, H_h(CBOR(["gsp/v0/key", K.alg, K.key])))`.
  A signature uses the hash algorithm of the id it signs.
- **`Signed`** is the envelope for ops, key-log entries and batches. `body` is
  the canonical encoding of the inner structure, carried as an opaque byte
  string. `sigs` MUST be sorted ascending by the bytes of each `Signature`'s
  encoding, MUST NOT contain two entries with the same `(alg, key_id)`, and
  holds at most 16 entries.
- **`fragment_id`** is an opaque byte string of 1 to 64 bytes.

### 3.1 Content ids

The id of an op, key-log entry or batch is

```text
id = Multihash(hash_alg, H_hash_alg(body))
```

where `body` is the byte string inside `Signed` **exactly as received** and
`hash_alg` is the field of that name inside the body. A receiver MUST hash the
received bytes. It MUST NOT decode and re-encode to obtain the id. The id is
not transmitted.

### 3.2 What a signature covers

```text
sig_input = CBOR([domain: tstr, audience: bstr, id: Multihash, alg: uint, key_id: Multihash])
```

| Signed thing  | `domain`          | `audience`                |
| ------------- | ----------------- | ------------------------- |
| op            | `"gsp/v0/op"`     | the op's `fragment_id`    |
| key-log entry | `"gsp/v0/keylog"` | empty byte string         |
| batch         | `"gsp/v0/batch"`  | the batch's `fragment_id` |

`alg` and `key_id` are those of the `Signature` entry being produced. The
signature is the raw algorithm output over the `sig_input` bytes (Ed25519:
pure Ed25519, no prehash; ML-DSA-65: `ML-DSA.Sign` with an empty context
string). CBOR's length prefixes frame every field, so no two different field
tuples produce the same bytes; the domain string separates object kinds; the
audience makes the fragment part of the signed bytes directly and not only by
way of the id.

A hybrid signature is two `Signature` entries, one per algorithm, over two
different `sig_input`s (they differ in `alg` and `key_id`).

## 4. Op

```text
OpBody = [
  format:      uint,              ; 0
  hash_alg:    uint,              ; HashAlg of this op's id
  fragment_id: bstr,              ; audience
  author:      Multihash,         ; id of the author's key-log genesis entry
  seq:         uint,              ; >= 1, position in the author's chain
  prev:        Multihash / null,  ; id of the author's op at seq-1
  hlc:         [wall_ms: uint, counter: uint],
  deps:        [* Multihash],
  payload:     any                ; any item allowed by section 1
]
Op = Signed                        ; body = CBOR(OpBody)
```

Structural rules (violations make the op `Invalid`):

- `seq >= 1`. `prev` is `null` if and only if `seq == 1`.
- `counter` fits in 32 bits.
- `deps` has at most 64 entries, sorted ascending by the bytes of each entry's
  encoding, no duplicates.

Semantics:

- **`seq` / `prev`** form one hash chain per author per fragment. Two
  different valid ops with the same `(author, seq)` are an **equivocation**
  (section 7).
- **`hlc`** is a hybrid logical clock: `wall_ms` is Unix milliseconds,
  `counter` breaks ties within a millisecond. Order is `(wall_ms, counter)`,
  then op id as a final tie-break. It MUST strictly increase along an author's
  chain. It orders concurrent writes; it says nothing about causality. There
  are no vector clocks in the signed format.
  - Local event: `wall' = max(wall, now)`; `counter' = 0` if `wall'` moved,
    else `counter + 1` (on 32-bit overflow: `wall' + 1`, counter 0).
  - A receiver with a clock treats an op whose `wall_ms > now + max_drift` as
    `Unverifiable` (reason `HlcTooFarAhead`) and MUST NOT merge that timestamp
    into its own clock. Default `max_drift` is 300 000 ms. Old timestamps are
    never rejected.
- **`deps`** are the heads (op ids, any author) the writer had applied when it
  wrote the op. This is the causality record. The author's own previous op is
  already named by `prev` and need not be repeated.
- **`payload`** is opaque to this layer.

## 5. Key log

Which keys an author has, and which signature algorithms the author requires,
come from the author's key log. They never come from the op being verified.

```text
KeyLogEntry = [format: uint, hash_alg: uint, prev: Multihash / null, action]
SignedEntry = Signed                           ; body = CBOR(KeyLogEntry)

action = [1, fragment_id: bstr, keys: [+ PublicKey], policy: [+ uint]]  ; Genesis
       / [2, key: PublicKey, from_seq: uint]                            ; AddKey
       / [3, key_id: Multihash, after_seq: uint]                        ; RevokeKey
       / [4, policy: [+ uint], from_seq: uint]                          ; SetPolicy
```

- The **author id** is the content id of the genesis entry. A key log, and so
  an author id, is bound to exactly one fragment. The same keys used in two
  fragments are two authors.
- `policy` is a strictly ascending list of 1 to 8 SigAlg ids. It means: every
  op MUST carry a valid signature for **each** listed algorithm. `[1]` is
  Ed25519 only. `[1, 2]` is hybrid.
- Positions are op sequence numbers, never wall-clock time:
  - a genesis key is valid from `seq` 1;
  - `AddKey`: the key may sign ops with `seq >= from_seq` (`from_seq >= 1`);
  - `RevokeKey`: ops signed by the key with `seq > after_seq` are invalid, ops
    with `seq <= after_seq` remain valid. `after_seq = 0` distrusts the key
    entirely. A second revocation of the same key can only lower `after_seq`;
  - `SetPolicy`: applies to ops with `seq >= from_seq`. The policy for an op
    at `seq` is the one with the greatest `from_seq <= seq`; among equal
    `from_seq`, the entry appended last.
- All entries of one log use the same `hash_alg`. `prev` is the id of the
  preceding entry (`null` only for genesis). `RevokeKey.key_id` uses that hash.

Accepting an entry (all MUST hold, otherwise the entry is rejected and the
log does not advance):

1. Genesis: every key listed signs the entry (proof of possession), there are
   no other signatures, and every algorithm in `policy` has at least one key.
2. Other entries: `prev` equals the current head. Every signature present
   verifies and is by a key of the log that has not been revoked (at any
   `seq`). The signatures cover every algorithm of the log's **most recently
   appended policy**. So a hybrid author's log cannot be extended with an
   Ed25519 signature alone.
3. `AddKey`: additionally the new key signs the entry.
4. After applying, every algorithm of the most recent policy still has at
   least one unrevoked key (an author cannot revoke itself into a state where
   no further entry could be authorised).
5. An entry using a format, action, hash or signature algorithm the
   implementation does not know is not applied; the log stays at its previous
   head on that implementation.

The 5.3 rule on Ed25519 below applies to key-log signatures too.

### 5.3 Ed25519 verification

Verification MUST be the strict variant: reject non-canonical `S`, and reject
small-order `A` and `R` (the behaviour of `ed25519-dalek`'s `verify_strict`).
JavaScript libraries differ here: the noble libraries verify with the more
permissive ZIP215 rules unless told otherwise (`zip215: false`), and whether
that setting also rejects small-order points has **not** been checked by this
project. A TypeScript port needs its own negative tests for this.
Implementations that disagree here will disagree
about which ops are valid.

## 6. Verifying an op

Input: the `Signed` bytes, the fragment they were received in, the verifier's
key logs, optionally the local clock. Output is exactly one of:

- **Valid**: may be applied.
- **Unverifiable(reason)**: keep the bytes, do not apply, try again when
  something changes (software, key log, clock).
- **Invalid(reason)**: rejected.

Steps, in order; the first that fires decides:

1. Parse `Signed` strictly. Failure: Invalid `Malformed`.
2. Parse `body` as `OpBody` strictly. `format != 0`: Unverifiable
   `UnknownFormat`. Other failure: Invalid `Malformed`.
3. Compute `id` from the received `body` bytes. Unknown `hash_alg`:
   Unverifiable `UnknownHashAlg`.
4. `fragment_id` differs from the fragment the op arrived in: Invalid
   `WrongFragment`.
5. No key log for `author`: Unverifiable `UnknownAuthor`. The log's fragment
   differs from the receiving fragment: Invalid `WrongFragment`.
6. Signature set, with `required = policy at seq`:
   1. `sigs` empty: Invalid `NoSignatures`.
   2. For each signature, look `key_id` up in the author's log.
      - Not found: remember it as _open_ (`UnknownKey`, or `UnknownSigAlg` if
        the algorithm id is unknown) and continue.
      - Found but not valid at `seq`: Invalid `KeyNotValidAtSeq`.
      - Found, `key.alg != sig.alg`: Invalid `AlgMismatch`.
      - Found, algorithm unknown to the implementation: _open_
        (`UnknownSigAlg`).
      - Otherwise verify over `sig_input`. Failure: Invalid `BadSignature`.
   3. For each algorithm in `required`: if no signature of that algorithm
      verified and no _open_ signature claims that algorithm, Invalid
      `MissingRequiredSignature`.
   4. If any signature is _open_: Unverifiable with the first open reason.
7. Clock supplied and `hlc.wall_ms > now + max_drift`: Unverifiable
   `HlcTooFarAhead`.
8. Valid.

Consequences worth stating:

- **Every signature present must verify.** One bad signature makes the op
  Invalid even if the policy would be satisfied without it.
- **Downgrade.** Removing the ML-DSA signature from a hybrid author's op gives
  `MissingRequiredSignature`.
- **Unknown is never valid.** An unknown algorithm anywhere yields
  Unverifiable, never Valid.
- `sigs` are outside the id, so a third party can append a junk signature to a
  valid op and make that copy Unverifiable. Receivers deduplicate by id and
  MUST let a Valid copy replace a retained Unverifiable copy of the same id.

Verification is stateless. Chain checks need history and are separate.

## 7. Chain checks and equivocation

Per `(author, fragment)`, for valid ops only:

- same `seq`, same id: duplicate;
- same `seq`, different id: **equivocation**;
- `prev` not equal to the id held at `seq - 1` (or the op held at `seq + 1`
  does not name this op as `prev`): the chain has forked; reject the op;
- `hlc` not strictly greater than at `seq - 1`: reject the op.

Ops may arrive out of order. An op is applicable only when every op from
`seq` 1 up to it is present.

```text
EquivocationProof = [a: bstr, b: bstr]    ; two Signed op encodings, a < b bytewise
```

The proof holds if both ops are Valid (verified without a clock) for the same
fragment, have equal `author` and `seq`, and different ids. Anyone holding the
author's key log can check it. What a fragment does with a proven equivocator
is policy above this layer.

## 8. Batch

```text
BatchBody = [format: uint, hash_alg: uint, fragment_id: bstr,
             sender: Multihash, sender_seq: uint, ops: [* bstr]]
Batch     = Signed                         ; body = CBOR(BatchBody)
```

Each element of `ops` is a complete `Signed` op; at most 1024. `sender_seq >=
1` is the `seq` of the sender's latest op when the batch was made (1 if none);
the sender's keys and policy are evaluated at that position. Verification is
section 6 steps 1 to 6 with domain `"gsp/v0/batch"`, `sender` in place of
`author` and `sender_seq` in place of `seq`. Only if the batch is Valid is
each op then verified individually (section 6); a Valid batch can contain ops
that are not Valid.

The batch signature authenticates the sender, the set and its order as a
unit. It does not replace the ops' own signatures.

## 9. Sealed op (what a relay sees)

Sign, then encrypt.

```text
Plain    = [kind: uint, bytes: bstr]       ; 1 = Signed op, 2 = Signed batch,
                                           ; 3 = Signed key-log entry (SignedEntry)
SealedOp = [format: uint, aead_alg: uint, fragment_id: bstr, nonce: bstr, ciphertext: bstr]
aad      = CBOR(["gsp/v0/sealed", format, aead_alg, fragment_id])
```

For AeadAlg 1: `nonce` is 24 bytes; `ciphertext = XChaCha20-Poly1305(key,
nonce, plaintext = CBOR(Plain), aad)` with the 16-byte tag appended (the usual
libsodium / RFC 8439 layout). `key` is the 32-byte fragment key.

- The nonce MUST be unique per key. Use 24 bytes from a CSPRNG.
- The receiver MUST check that `fragment_id` is the fragment it expects, then
  decrypt, then run section 6 (kind 1), section 8 (kind 2) or the key-log
  acceptance rules of section 5 (kind 3) on the result. Decrypting proves only
  that the sender held the fragment key. Any other `kind` is a decode error.
- Kind 3 carries one `SignedEntry` so that key logs travel through a relay
  under the same encryption as ops. A genesis entry names its fragment inside
  the signed body; the receiver MUST check that it equals the `fragment_id` of
  the sealed header it arrived in.
- A relay learns: fragment id, nonce, ciphertext length, timing. It does not
  learn author, `seq`, clocks, key ids, signatures or payload. There is no
  length padding in v0.

## 10. Frames

Each frame is one CBOR item `[type: uint, ...]`. How frames are delimited on a
transport is not defined here.

```text
Hello = [1, versions: [* uint], sig_algs: [* uint], hash_algs: [* uint],
            kem_algs: [* uint], aead_algs: [* uint], nonce: bstr]
Auth  = [2, fragment_id: bstr, author: Multihash, sender_seq: uint, sigs: [* Signature]]
Push  = [3, fragment_id: bstr, sealed: [* SealedOp]]
Pull  = [4, fragment_id: bstr, after: uint, limit: uint]
Batch = [5, fragment_id: bstr, next: uint, more: bool, sealed: [* SealedOp]]
Ack   = [6, fragment_id: bstr, cursor: uint, count: uint]
Head  = [7, fragment_id: bstr, cursor: uint]
Error = [8, code: uint, message: tstr]
```

`SealedOp` is embedded as an array, not wrapped in a byte string. Cursors are
positions assigned by one relay to the sealed ops of one fragment, strictly
increasing, starting above 0; `after = 0` means from the start. `limit` and
`count` fit in 32 bits, `code` in 16. An unknown `type` is a decode error.

**Not yet specified** (types exist so the CBOR is fixed; behaviour is not):
the exact bytes `Auth.sigs` sign, the `Error.code` registry, and the
`Hello` negotiation rules. Do not ship an `Auth` implementation against this
document.

## 11. Known limits of v0

Stated so that nobody assumes otherwise:

- **Genesis trust is external.** The key log proves internal consistency. It
  does not prove that an author id belongs to a person or DID.
- **Key-log forks.** An author (or a thief of all its current keys) can sign
  two different entries with the same `prev`. Each peer follows the first one
  it sees. Two peers comparing heads can notice; there is no proof format or
  resolution rule for it yet.
- **Stale logs cut both ways.** A verifier that has not yet received a
  `RevokeKey` accepts ops it would later reject (the revocation test shows the
  same bytes going from Valid to Invalid). Appliers need to be able to
  re-evaluate.
- **A revoked key can still sign at `seq <= after_seq`.** Whoever holds it can
  mint ops at old positions. Peers that already hold the original op at that
  `seq` see an equivocation; a peer that has nothing at that `seq` cannot tell.
- **Compromise of a full policy set is total.** Whoever holds one unrevoked
  key per required algorithm can add keys and revoke the owner's.
- **ML-DSA signatures are deterministic** here, and `ml-dsa` 0.1.x is
  unaudited. See the crate documentation.
- **Size.** A hybrid op carries about 3.4 kB of signatures. Signing only the
  head of an author's chain per batch would remove most of that; not in v0.

The value, written in no particular order:
